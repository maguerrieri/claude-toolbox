# Launch model (the `Session model:` lines)

The one definition of how a launch's model is chosen, read on demand by whatever is about to launch a session: SPAWN Step 3 (`phases/spawn.md`) for siblings, `phases/epic.md` Step 5 for an epic's children, and `/spawn-epic` for the orchestrator it launches. It is a file of its own, like `messaging.md`, so that the `/spawn-epic` launcher can read these rules without the rest of SPAWN.

- **The lines.** `Session model: <model>` covers every session this skill launches. `Session model (<role>): <model>` covers launches of one role: `epic-coordinator` (the orchestrator `/spawn-epic` launches) or `implementer` (SPAWN's siblings, EPIC's children). A line naming any other role (`Session model (coordinator):`, `Session model (planner):`) applies to nothing: name it in the launch report, so a misspelled role isn't taken for one in effect. Each sits on a line of its own, like `Tracker:`. The key is `Session model`, never a bare `Model:`, which a repo's instructions may use for something of their own (the model its app calls, say) and which is not read.
- **The sources**, highest priority first: project memory, then root `AGENTS.md`, then the root `CLAUDE.md` / `.claude/CLAUDE.md` fallbacks (the three `SKILL.md` Step 0 reads its other optional settings from), then one more that only these lines have: the user-level `CLAUDE.md` in the Claude config directory (`~/.claude/CLAUDE.md`, or `$CLAUDE_CONFIG_DIR/CLAUDE.md`), the user's global instructions, which every session of that user already has in context. A line there is the user's default across every repo, so one line can map a role to a model everywhere, and a repo's line of the same kind overrides it (*Resolution*, below). A session with no such file (a cloud session, usually) has three sources.
- **Read the sources when you resolve.** The copy of an instruction file in your context is the one loaded when your session started, and a long-lived coordinator's can be days old. So Read each file again at resolution time: the memory index and the memory it points to, the repo files in the repo's main checkout (the durable launch directory, where the launched session starts, not a ticket worktree on another branch), and the user-level file.
- **No line means no model.** The launch passes no `--model` flag and no `model` field, exactly as before these lines existed, and the session runs on Claude Code's default.
- **Who resolves, and when.** The spawner, for the role it is launching, once per run (one fan-out, one epic run, one `/spawn-epic`), before its first launch, so every launch of that run carries the same model. A later run, or a coordinator re-entering its epic, resolves again. Nothing rides the briefing: a coordinator inherits the config home and resolves the implementer model itself, and the model `/spawn-epic` gave it says nothing about its children's.
- **Resolution: the role's line first, wherever it is.** Two passes over the sources, each in the order above. First look for the role's own `Session model (<role>):` line, and take the first valid value. Only when no source has one, look for the plain `Session model:` line the same way. So **a role line is never overridden by a plain one**, whichever source each sits in: a plain line in project memory doesn't displace a role line the repo commits, and a repo's plain line doesn't displace a role line in the user-level file. Source order decides only between lines of the same kind: project memory over the committed instructions, as for `Tracker:`, and both over the user-level file. The value `default` ends the pass it is found in, with no model, which is how a line switches off the lines of its kind below it. On a role line that is final: `Session model (implementer): default` means no model for implementers, and the plain lines aren't consulted. On a plain line it only matters when no role line exists.
- **Validation.** The value lands in a shell command, so take it only when it is a model alias or ID and nothing else, matching `^[A-Za-z0-9][A-Za-z0-9._-]*(\[[A-Za-z0-9]+\])?$`: letters, digits, `.`, `_` and `-`, plus an optional bracketed suffix such as `[1m]`. Skip any other value, go on to the next line, and name the skipped line in the launch report, as for a malformed `Budget:`. A model ID with other characters (a Bedrock ID's `:`, a Vertex ID's `@`, an ARN) doesn't pass; such a setup sets its model in Claude Code's own settings instead. The pattern checks shape, not existence: a mistyped alias (`sonet`) passes it, so if a launch errors on the model, report that unit as failed rather than launched.
- **Passing it.** On the local backend, add `--model "<model>"`, quoted, right after `--bg`, and change nothing else in the launch command: the `( cd "$launch_dir" && env -u CLAUDE_SESSION_ID … )` wrapper, the name and the prompt stay as each phase shows them (under zsh an unquoted `[1m]` is a glob). As `"model": "<model>"` on cloud. The `spawn` skill's backend files show both.
- **Cloud caveats, neither verified.** `create_session` may not accept every alias the CLI does. If it rejects the model, report the failed launch and don't relaunch without one: a silent fallback would run the session on a model nobody chose. And a call that omits `model` is documented only as "inherits" (the `spawn` skill's `backends/cloud.md`). If that means the spawner's model, an orchestrator launched on a `Session model (epic-coordinator):` model passes it on to children that have no line of their own, where a local child would get the default. Set `Session model (implementer):` as well where that matters.
- **A resume never passes a model.** Any flag besides `--bg` next to `--resume` starts a copy of the session (the `spawn` skill's `backends/local.md`, *Resume*), and a resumed session keeps the model it was launched with. So a changed line applies to new launches only, and a report never claims the newly resolved model for a resumed row.
- **What the lines don't cover.** A generic `/spawn` unit or an implementer's helper session (the `spawn` skill takes a model only from its caller or the user's ask), in-process subagents, and Projects mode, which launches nothing. A `Session model (planner):` line applies to nothing, since no spawn edge launches a planner: start one on a model yourself (`roles/planner.md`, *Setting this role*).
- **The lines are the only input.** A model named in a `/spawn-tickets`, `/start-epic` or `/spawn-epic` request is briefing text, passed on as written, and picks no launch model: which role it would cover isn't something a request says. To run one fan-out on another model, add the role's own line (`Session model (implementer): <model>`) to project memory first, and remove it afterwards: a role line there outranks every other line for that role, where a plain one would lose to any role line a lower source carries.
